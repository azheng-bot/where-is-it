## Context

现有工程包含 Web、API 和 `services/vision`。API 保存物品、观测和证据，视觉服务以固定 mock 图循环上报观测；DeepSeek 是 API 通过兼容接口调用的外部云端 LLM。参见 [proposal.md](proposal.md) 的动机，以及新增规范中的行为契约。

线上 VLM、检测、分割、向量检索与 ASR 的模型大小、GPU 占用、依赖栈和升级频率不同。它们不能与 API 共享进程，也不应各自访问物品 SQLite 数据库。首版仍必须可以在没有 GPU 或真实模型权重时完成从 mock 摄像头到画面标注和问答的演示。

## Goals / Non-Goals

**Goals:**

- 将 GPU 模型与 API、Web、以及无 GPU 的视觉编排器隔离，并允许每个模型服务独立配置地址、镜像、模型版本和资源。
- 以共享的内部契约传递帧/媒体引用、关联 ID、截止时间、模型版本、状态与归一化结果。
- 让 API 保持物品事实、证据和查询的唯一写入点；模型服务只做无状态推理。
- 对单次用户查询提供五秒内的可用回答：优先已有事实和最近证据，模型链路超时则明确降级而非等待无限期或伪造结果。
- 在本地保留可插拔 mock 适配器，使开发和演示无需下载 GPU 模型。

**Non-Goals:**

- 不在本变更中选择或训练具体模型、调优模型准确率，或保证多模型在单张 GPU 上的精确显存并发配额。
- 不引入多摄像头、跨房间身份系统、通用任务队列、服务网格或生产级自动扩缩容。
- 不更改 DeepSeek 的云端 LLM 提供方边界，也不将其作为本地 GPU 微服务。

## Decisions

### 1. 分层拓扑：API 为事实中心，orchestrator 为视觉入口

拓扑如下：

```
摄像头/mock frame
       │
       ▼
vision-orchestrator (CPU)
  ├─ Florence service      (GPU 可选)
  ├─ Grounding service     (GPU 可选)
  ├─ SAM service           (GPU 可选)
  └─ Embedding service     (GPU 可选)
       │ 标准 ObservationBatch
       ▼
API ── SQLite/证据文件 ── Web
 │
 ├─ DeepSeek（外部云端 LLM）
 └─ ASR service（GPU/CPU 可选）
```

`vision-orchestrator` 仅协调帧处理、调用模型、校验结果和上报 API；它不保存用户可查询事实。模型服务不调用 API 或数据库。这样 API 能在视觉服务部署、重启或升级时持续提供“最后出现”与“未检测到”回答。

备选方案是继续把所有模型放在 `services/vision` 进程。该方案启动简单，但模型依赖和显存互相影响，无法独立扩缩容或灰度版本，因此不采用。

### 2. 统一版本化 HTTP 契约和媒体引用

新增 `packages/contracts`（或现有 contracts 包的内部子模块）定义 Pydantic/TypeScript 对应的请求与响应 JSON 模式。每个请求包含：`request_id`、`contract_version`、`deadline_ms`、`source`、`frame_ref` 或 `media_ref`，以及可选的查询文本。响应包含相同 `request_id`、`model_version`、`status`（`ok` / `degraded` / `failed`）和结构化结果/错误码。

原始图像通过可访问的文件、对象存储 URL 或内存上传端点引用传递，不在串行模型调用中反复 base64 复制。开发环境可使用受限的本地文件引用，线上环境改为短时有效的内部对象存储引用。编排器在服务边界验证版本、关联 ID 和截止时间后才上报观测。

备选方案是每个模型自定义 JSON，或把图像字节随所有请求传递。前者会使编排难以演进；后者会放大内存和网络成本，因此不采用。

### 3. 模型服务采用一致的最小运行接口

所有服务提供 `/health/live`、`/health/ready` 和 `/v1/infer`。服务由自身配置公开模型名、版本、设备与并发上限；`/v1/infer` 的有效负载按模型类型不同，但共享外层元数据和错误模型。服务启动完成但权重未加载时 live 成功、ready 失败。内部调用设置连接超时与请求总时限，且将 `request_id` 写入结构化日志。

备选方案是 gRPC 或统一消息队列。HTTP 更贴合现有 FastAPI 服务、易于本地演示和健康探测；吞吐压力出现后可在不改变上层契约语义的情况下迁移到 gRPC 或异步队列。

### 4. 模型编排使用阶段性降级，保护五秒响应目标

编排器将发现、定位、分割、嵌入视为可选阶段：Florence 产生候选，Grounding 验证目标，SAM 提供掩码/框，Embedding 用于需要相似检索时才调用。每阶段遵守父请求的剩余时间预算；关键阶段失败则产生失败/降级状态，不上报未验证位置。

面向用户的查询优先由 API 检索已有的已确认观测和证据，LLM 只根据这些事实组织答案。若新帧推理未在预算内完成，API 返回最近已确认事实或明确的“尚未检测到”，并保留关联状态供后续观测更新。这样可避免模型延迟把一次查询卡住超过五秒。

备选方案是等待完整多模型流水线再回答。它可能提升新帧精度，但不满足交互响应目标，也会把单模型故障扩散给用户查询。

### 5. ASR 独立于网页和 API 进程

Web 继续采集音频并提交给 API；API 验证大小、格式和时限后转发给 ASR 服务。ASR 返回文本、语言（若可用）、置信信息和标准错误。API 使用成功文本调用与键盘输入相同的查询逻辑；ASR 不可用时返回明确的语音处理失败，文字输入不受影响。

备选方案是浏览器 Web Speech 或在 API 内嵌 faster-whisper。浏览器能力在不同环境不稳定且难以统一审计；API 内嵌模型会重新耦合 GPU 依赖，因此不采用作为主路径。浏览器原有 mock 可保留为开发显式开关。

### 6. 本地 mock 是服务适配器，不是前端特例

将现有 `bedroom-mock.png` 和固定检测框迁入 orchestrator 的 `mock` 适配器。它实现与真实模型链路相同的归一化输出和 `ObservationBatch`，由环境变量选择。前端始终从 API 获得 `evidence_url`、`bounding_box` 和状态；不再在前端维护图像专用物品坐标。

备选方案是在浏览器中伪造识别框。该方案无法验证 API、证据和服务边界，因此不采用。

## Risks / Trade-offs

- [多服务增加本地启动复杂度] → 提供统一 compose 配置、健康检查、默认 mock 模式和单命令开发入口。
- [单 GPU 同时加载模型可能 OOM] → 模型服务独立容器、显式设备/并发配置；默认按需启用服务，不承诺同卡并发全量加载。
- [帧引用泄露或跨服务不可访问] → 内部网络隔离、短时引用和访问路径校验；生产环境使用私有对象存储。
- [模型服务慢于五秒] → 阶段性超时、API 优先历史事实、可识别降级码与可观测关联日志。
- [微服务间版本漂移] → 契约版本字段、兼容性测试和按服务模型版本记录。
- [ASR 误转写造成错误查找] → 仅以成功转写文本执行查询，向用户展示转写文本；失败时不猜测。

## Migration Plan

1. 抽取现有观测 DTO 和 mock 帧适配器，先让 `vision-orchestrator` 用同一批 mock 数据调用现有 API；保持浏览器 API 响应不变。
2. 建立服务模板与内部契约，默认所有真实模型服务关闭或使用 mock 后端；为 API 增加 ASR 客户端的显式配置。
3. 依次接入 Florence、Grounding、SAM、Embedding 的真实实现，每接入一个服务都用契约和降级集成测试验证，不让未验证结果入库。
4. 启用 ASR 服务和语音端到端测试；保留键盘查询作为独立的无 ASR 路径。
5. 在线上先部署 API + orchestrator + mock，随后按 GPU 容量逐个启用模型服务并观测就绪、时延、错误和显存。

回滚时，将 orchestrator 运行模式切回 mock，或把具体模型服务地址设为未启用；API 继续读取已有事实。移除新版服务不需要回滚数据库架构，因为模型服务不拥有持久化数据。

## Open Questions

- 线上对象存储提供方和帧引用签名方案将在部署环境确定后选择；不改变本设计的“短时内部媒体引用”契约。
- 首批真实模型的模型权重、精度模式和 GPU 类型将在容量测试后确定；服务边界和错误语义保持不变。
