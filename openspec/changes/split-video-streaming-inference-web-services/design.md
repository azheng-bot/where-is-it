## Context

当前工作区已有 Web、API、视觉编排器、四个视觉模型服务及 ASR 服务。Compose 将这些运行单元并列启动；远端 GPU 配置也已采用“边缘推送 JPEG 帧、GPU 接收”的传输方式，但 API 和 ASR 仍是独立服务。详见 [proposal.md](proposal.md) 的变更动机以及本变更的规格增量。

约束：首版为单摄像头、单卧室 PoC；采集侧可没有 GPU；GPU 节点基线为单张 24GB RTX 40 系列显卡；帧不能形成视频归档或无界队列；API 是观测事实、SQLite 数据和证据图片的唯一写入方。Web 的麦克风采集、文字输入和浏览器端语音播报继续在浏览器中完成；服务端 ASR 仅负责上传音频的转写。LLM 仍是 GPU API 服务调用的受控依赖，不能改变事实写入规则。

## Goals / Non-Goals

**Goals:**

- 交付三个可独立构建、配置、部署、检查和回滚的服务包：`video-streamer`、`gpu-inference-api` 与 `web`。
- 将 API、帧接收、视觉运行时、ASR 及其模型缓存收进同一个 GPU 部署边界，同时保留当前的内部请求追踪、模型版本和降级信息。
- 保持 Web 对 API 的查询契约、物品状态分层、语音查询语义及证据读取行为兼容。
- 只公开 Web 静态站点、GPU API 的业务端点及受认证的帧接收端点；内部模型/ASR 端口仅供同一 GPU 服务包内部使用。
- 在帧处理或模型不可用时，以最新帧丢弃、既有事实查询和清晰健康状态实现可控降级，支持五秒查询目标。

**Non-Goals:**

- 不把本地推流端改造成录制器、消息总线或多摄像头汇聚器。
- 不将模型组件强制合并为单一 Python 进程；它们可在 GPU 服务包内以受管理子进程或私有容器保留隔离。
- 不引入新的用户认证、设备配对、TLS 终止实现或云部署平台；这些由部署环境提供。
- 不改变数据库数据模型、物品/位置稳定 ID、事实证据规则或浏览器的语音播报实现。

## Decisions

### 1. 以“部署单元”而非“单一进程”定义三个服务

`video-streamer` 运行在摄像头可达的边缘设备；`gpu-inference-api` 运行在 GPU 节点；`web` 可运行在静态站点或 Web 服务器。GPU 服务包内部可以继续启动 API、视觉编排、模型和 ASR 进程，但它们共享内部网络、模型缓存、数据卷和统一的外部入口，用户只部署一个 GPU 服务包。

理由：保留独立模型进程对显存、启动失败和模型升级的隔离，同时消除面向部署者的多服务编排复杂度。替代方案是把所有能力并入一个 Python 进程；这会放大模型崩溃和依赖冲突的影响。维持现有全部独立部署则不能满足目标服务拓扑。

### 2. 帧传输保持“最新 JPEG + 推送认证”模型

推流服务以单个可替换视频源产生 JPEG，通过 `POST /v1/frames` 和推送令牌发送至 GPU 服务。接收端保留最新可处理帧；传输失败或 GPU 过载时丢弃当前帧并在下个采样周期重试，不引入本地磁盘缓存或队列。

理由：该模型适合单摄像头实时发现，能限制带宽、内存和隐私风险。替代方案是公开 RTSP 或引入 Kafka/对象存储；前者扩大网络攻击面，后者会引入录像数据与运维成本，均超出 PoC。

### 3. GPU 服务以 API 为唯一公开业务入口和事实写入者

GPU 服务以 API 进程承载物品查询、证据读取、观测持久化和语音查询端点。帧接收经视觉编排和模型运行时返回归一化候选观测，由 API 按现有证据规则写入 SQLite 和证据目录。ASR 将音频转写结果送入同一查询入口；浏览器端仍负责录音与播放。

理由：避免模型或 ASR 直接修改事实，保持“当前检测、最后出现、推测位置”可解释。替代方案是让推流服务直接写数据库或模型直接提供 API；会破坏唯一事实写入边界。

### 4. 分离公开地址、内部地址和健康状态

配置将定义 `PUBLIC_API_URL`（Web 使用）、`FRAME_INGEST_URL`（推流使用）和 GPU 服务内部运行时地址。Compose 仅发布 GPU 服务的 API 和帧接收端口；模型、ASR 与内部编排端口不映射到宿主机。GPU 根就绪检查汇总 API、关键视觉组件和 ASR 的状态，并保留只供运维的组件明细；推流与 Web 各自提供独立的存活/就绪检查。

理由：减少端口暴露且让部署系统能判定可用能力。替代方案是直接公开各内部端口用于排障；这会将内部契约锁定为外部接口并扩大攻击面。

### 5. 通过服务包 Compose 配置完成迁移

新增或重组为三个命名明确的 Compose 构建目标和启动脚本：边缘推流包只包含采集依赖；GPU 包包含 API、接收器及私有运行时；Web 包只包含前端构建产物和 API 地址注入。GPU 包只接受真实 NVIDIA GPU 运行时和真实模型/ASR，不提供 CPU 或 mock 后备配置。

理由：一个仓库中继续共享代码、契约和测试，而部署者不必理解内部模型服务。替代方案是立即拆分为多个代码仓库；它会增加版本协同和本变更的迁移风险，暂不需要。

## Risks / Trade-offs

- [同一 GPU 包内组件启动顺序或依赖失败] → 使用聚合就绪检查、组件级诊断和受控重启；API 在无新观测时仍返回历史事实。
- [视觉模型与 ASR 争抢显存或计算时间] → 维持模型最大并发为一、提供模型/ASR 资源配置，并在超过时限时返回明确降级而非阻塞查询。
- [推流端与 GPU 节点网络中断] → 推流端丢弃失败帧并暴露最近失败状态；GPU API 标记观测可能过期，不伪造当前检测。
- [Web 部署地址配置错误或 CORS 限制] → 将公开 API 地址和允许来源作为显式环境变量，并在 Web 就绪检查中验证可用的 API 配置。
- [现有脚本依赖独立端口] → 在迁移期保留内部兼容启动命令，但不将其列为生产部署接口；完成合同测试后移除或标注为开发诊断用途。

## Migration Plan

1. 盘点现有启动脚本、Compose 服务、环境变量和端口消费者，建立公开端点与内部端点的兼容清单。
2. 提取 `video-streamer` 构建入口，将视觉编排器固定为 pusher 角色并验证 USB、RTSP 和 mock 输入。
3. 建立 `gpu-inference-api` 服务包：以 API 为入口，接收帧并编排私有视觉/ASR 运行时，挂载既有数据和模型缓存卷，增加聚合健康检查。
4. 调整 Web 为只读取公开 API 地址；验证文字查询、麦克风上传、语音播报、证据查看与 API 跨域配置。
5. 在真实 GPU 节点执行三服务契约与故障测试，验证模型就绪、显存门槛、帧推送、语音查询和五秒响应降级；缺少 GPU 或模型时服务必须明确未就绪，而非降级到 CPU/mock。
6. 更新运行手册和样例环境文件，停止在生产说明中暴露旧模型与 ASR 端口，完成一次从旧 Compose 启动方式到三服务方式的演练。

回滚：保留当前多进程 Compose 配置及现有数据卷不变；若 GPU 服务包健康检查或合同测试失败，可将 Web 的 API 地址和推流目标恢复到旧入口。迁移不改写业务数据库，因此无需数据回滚。

## Open Questions

- GPU 服务的公开 API 与帧接收端点是否在同一反向代理域名下使用不同路径，还是分别使用两个受控入口，可由实际网络拓扑在部署时确定；两种方式不改变本设计的服务边界。
