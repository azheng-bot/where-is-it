## Why

当前工程虽已包含推流、视觉模型、ASR、API 和 Web，但它们以多个可单独启动的进程和 Compose 服务交织部署。实际交付时，这会增加跨主机配置、端口暴露和运维复杂度，也不符合“采集端、GPU 节点、浏览器端”三类运行环境的部署方式。需要将运行时收敛为三个边界清晰、可独立交付的服务。

## What Changes

- 将系统部署拓扑收敛为三个服务：部署在摄像头侧的**视频推流服务**、部署在 GPU 节点的**视频推理 + ASR + API 服务**、以及独立部署的**Web 前端服务**。
- 视频推流服务只负责从 USB、RTSP 或 mock 视频读取帧、压缩并鉴权推送；不保存视频、不运行模型、不访问业务数据库。
- GPU 服务接收最新帧，在其私有运行时内完成视觉推理、语音转写和 API 业务处理；模型与 ASR 的内部实现可保留为受编排的进程或容器，但不再作为需要用户单独部署或暴露的产品服务。
- Web 服务仅通过公开 API 提供查询、结果、证据和语音交互；不直接访问摄像头、推流端或内部模型端口。
- 更新 Docker Compose、环境变量、健康检查、网络访问策略和运行手册，使三个服务可以分别构建、启动、升级及排障。

### 首版范围与非目标

- 首版保留单摄像头、最新帧处理、现有物品查询语义和“当前检测 / 最后出现 / 推测位置”的事实分层。
- 本变更不引入多摄像头、多用户、视频录像归档、消息队列或公网身份认证产品能力；反向代理、TLS 与部署平台配置仅定义必要接口和边界。

## Capabilities

### New Capabilities

- `three-service-deployment-topology`: 定义视频推流、GPU 推理 API 和 Web 前端三个可独立部署服务的职责、连接方式、公开接口和运行边界。

### Modified Capabilities

- `model-service-boundaries`: 将视觉编排及模型运行时收敛为 GPU 推理 API 服务的私有组件，同时保持模型故障可观察和结果可降级。
- `asr-service-boundary`: 将语音转写收敛到 GPU 推理 API 服务边界内，保持 API 的语音查询语义和失败保护。
- `internal-inference-contract`: 明确 API 与内部视觉/ASR 运行时的调用在 GPU 服务内部完成，且不改变观测事实唯一写入方的约束。

## Impact

- 受影响代码：`services/vision-orchestrator`、各视觉模型服务、`services/asr`、`services/api`、`apps/web`、workspace 启动脚本与 Docker Compose 文件。
- 部署形态从多个服务容器调整为三套可交付服务包；GPU 服务内部仍需共享模型缓存、API 数据卷及 GPU 资源配置。
- 受影响接口：推流上传、API 对 Web 的公开端点、健康检查，以及 GPU 服务内部的视觉和 ASR 调用；公开模型端口将被移除或限制为私网调试用途。
