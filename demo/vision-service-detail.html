视觉服务如何工作

持续看，低频发现，稳定后才写入位置记忆。

视觉服务与问答 API 分离。它在后台消费最新视频帧，生成稳定的结构化观测，再批量提交给业务 API。

当前仓库实际状态

服务已经是独立 FastAPI 进程，支持健康检查、摄像头来源枚举和模型适配器边界。模型推理、视频采集、跟踪与事件提交尚未落地，目前返回 cpu-demo 状态。

目标运行链路

查询路径不等待视频帧推理

1. 采集最新帧

采集线程仅维护最新画面。旧帧丢弃，不建立连续录像队列。

target 1280 × 720
旧帧可丢弃，避免推理积压

2. 分层视觉流水线

不同模型各自处理最擅长的任务，避免逐帧调用通用大模型。

重型发现 每 1-2 秒Florence-2 提取区域描述和属性，Grounding DINO 用开放词汇复核物品与家具候选。
掩码与跟踪 中间帧SAM 2.1 将框转成掩码，在相邻帧传播具体目标。CPU 模式可降级为轻量框跟踪。
重识别 候选出现时DINOv2 向量结合颜色、OCR、类别和空间距离，确认是否仍是同一个 object_id。
位置归属 稳定后将物品掩码与已知区域的交叠、底部中心点和层级关系转成确定位置。
→

3. 稳定观测事件

视觉服务不直接写数据库，而是批量将类型化事件提交给 API。

observation物品、位置、时间、置信度、bbox 或 mask、track_id。
stable observation最近五次发现中至少命中三次，才升级为正式或待确认对象。
POST internal observationsAPI 维护 object_state、observations 和必要的证据图片。
identity_uncertain第一、二名相近或分数不足时，只记录不确定性，不覆盖确定位置。
选择一个场景以高亮数据路径 idle

稳定规则与状态变化

这是设计中要求的保守写入策略，避免一帧误检把“最后出现位置”误写成“当前存在”。

发现晋级最近 5 次重型发现中至少命中 3 次，才能成为稳定物品或待确认对象。
新鲜窗口最近确定观测不超过 3 秒，查询可表述为当前检测到。
不可见宽限连续 5 秒无法匹配，状态转为 not_currently_detected。
身份保护相似物品、遮挡后重现或低分匹配都进入 identity_uncertain，不写确定位置。

提交给 API 的观测形状

实际 HTTP schema 尚未实现，下面展示该服务边界应传递的核心字段。

{
  "object_id": "01J...",
  "observed_at": "UTC ISO-8601",
  "track_id": "sam-track-17",
  "location_id": "bedside-table-left",
  "confidence": "high",
  "identity_state": "confirmed",
  "evidence": { "bbox": [x, y, w, h] }
}
API 是 SQLite 和证据文件的唯一写入者。视觉服务可重启，不会破坏已有位置记忆。
当前已实现：FastAPI 进程、USB / RTSP / fixture 来源枚举、模型 Adapter 占位接口、健康状态端点。待实现：真实模型加载、采集线程、观测 schema、内部提交、稳定状态机和 CPU / GPU profile。
